# Sample Size Calculator

Power analysis and sample size determination for study design. One
statistical engine, written in C++17, serves three ways of using it:

- **A web page** that calculates in your browser: the engine compiled to
  WebAssembly, so nothing you type leaves the page. It works on phones, too:
  <https://hyungrok-do.github.io/sample-size-calc/>
- **A command line** (`ssc-calc`) and a Python library (`ssc`), on Windows,
  macOS and Linux.
- **An MCP server** (`ssc-mcp`) that lets language-model clients such as
  Claude and ChatGPT find a method and calculate, with the engine doing the
  arithmetic.

All three give the same answers, from the same engine, which is validated
against R and published results ([Validation](#validation)).

Note that this project has largely been generated by claudecode and under validation.

## Highlights

- **71 procedures**: means (co-primary endpoints included), proportions and
  case-control studies, correlation and regression (clinical prediction models
  included), survival, rates and counts, variances, nonparametric tests,
  group-sequential designs, agreement and diagnostic accuracy, precision of
  confidence intervals, cluster-randomized trials and simulation-based designs
  ([full list](#procedures)).
- **Solve for** sample size, power or the detectable effect. Any numeric input
  may be a list (`0.8 0.9`) or a range (`10 to 100 by 10`). The scenarios are
  computed in parallel and reported as one table, with power curves.
- **Exact methods where they matter**:
  - noncentral t, F, χ² and beta distributions;
  - exact power by enumeration for binomial, Fisher, McNemar and the sign test;
  - exact TOST power for equivalence;
  - the exact distribution of the correlation coefficient;
  - group-sequential boundaries by recursive numerical integration, with
    α- and β-spending, binding or non-binding futility.
- **Simulation when formulas fall short**: power and sample size, by
  simulating whole studies and analyzing each one the way the real study will
  be analyzed:
  - longitudinal and cluster-randomized trials with linear mixed models (REML,
    Satterthwaite t-tests), with dropout between visits and unequal cluster
    sizes;
  - repeated measures with dropout analyzed by an MMRM (unstructured
    covariance, the difference at the last visit);
  - stepped-wedge trials with period effects and a cluster autocorrelation
    (Hussey & Hughes, or Hooper's cluster-period effects);
  - clustered yes/no outcomes with logistic mixed models (adaptive
    Gauss–Hermite quadrature);
  - survival with delayed, waning or crossing effects (logrank,
    Fleming–Harrington, MaxCombo and restricted-mean tests);
  - skewed, heavy-tailed or outlier-prone data (t, Welch and Mann–Whitney on
    the same simulated studies);
  - ordinal outcomes such as the modified Rankin Scale (proportional odds
    model, likelihood-ratio and Mann–Whitney tests);
  - several treatments against a control (Dunnett, Holm, Hochberg,
    Bonferroni; power to find any, all or each effective treatment);
  - hierarchical composite endpoints (the win ratio and the
    Finkelstein–Schoenfeld test).

  Thousands of simulated studies run in parallel in a fraction of a second;
  results come with their Monte Carlo standard error, are reproducible from a
  seed, and can be previewed by an analytic approximation.
- **Reports**: summary sentences, result tables, sample sizes inflated for
  dropout, boundary tables, definitions and references. The command line also
  writes CSV, JSON and a Word document (.docx) ready to edit into a protocol
  or a grant application.
- **A search that understands** typos, abbreviations and synonyms
  ("logrnk", "NI proportions", "κ", "margin of error").
- **Validated** against R (`stats`, `pwr`, `rpact`), high-precision `mpmath`
  values and published results ([Validation](#validation)).

## Installation

### The web page

Nothing to install: open
<https://hyungrok-do.github.io/sample-size-calc/> in any browser
updated since 2022 (Chrome, Edge, Firefox, Safari, on computers and phones).
After the first visit it also works offline. [`web/README.md`](web/README.md)
explains how to build and serve it yourself.

### The Python package: command line, library and MCP server

Requirements: Python 3.9 or later, plus a C++17 compiler and CMake 3.15+ to
build the engine.

| Platform | Compiler |
|---|---|
| Windows | Visual Studio 2019 or later, or the *Build Tools for Visual Studio* ("Desktop development with C++") |
| macOS | Xcode Command Line Tools: `xcode-select --install` |
| Linux | GCC 8+ or Clang 7+ |

Install it into the repository's own virtual environment, `.venv`, with
`scripts/setup_venv.py`, so its commands run from one place, whatever else is
installed:

```bash
git clone https://github.com/hyungrok-do/sample-size-calc.git
cd sample-size-calc
python3 scripts/setup_venv.py          # makes .venv and installs the package into it
source .venv/bin/activate              # Windows: .venv\Scripts\activate
ssc-calc --help
```

On Windows, run the script with `py scripts\setup_venv.py`. With conda, run
`conda deactivate` first, so that conda's environment and `.venv` do not mix.
After a `git pull`, run the script again to bring the installation up to
date; `--fresh` deletes `.venv` and starts over, and `--tests` also installs
pytest. To install into another environment instead, run
`python -m pip install .` there (`".[mcp]"` adds the MCP server's SDK).

`pip` compiles the engine with CMake (through scikit-build-core) and installs
the `ssc` package with two commands, `ssc-calc` and `ssc-mcp`. Python talks to
the engine through a plain C interface (ctypes), so one build serves every
Python 3 version on that platform.

Prebuilt wheels need no compiler. The *Wheels* workflow builds them for Windows
x86-64, macOS (universal2) and Linux x86-64 and aarch64 (glibc 2.28 or later),
and they install with `python -m pip install sample_size_calculator-*.whl`.

## Usage

### Web page

Search for a method or pick one from the list, choose what to solve for, fill
in the inputs and press **Calculate**. Every input has a short explanation,
any number can be a list or a range, and a long simulation can be stopped.
On a computer with several cores, simulations use all of them.

### Command line

```bash
ssc-calc search equivalance two means           # ranked; typos and synonyms are fine
ssc-calc list --search survival
ssc-calc show means.two.t                       # parameters, choices, example
ssc-calc run means.two.t --solve n power="0.8 0.9" mu1=1 mu2=0 sigma=1
ssc-calc run gs.means --example alternative=upper alpha=0.025 futility=beta
ssc-calc run prop.two --solve power n1="20 to 200 by 20" p1=0.6 p2=0.4 --csv > power.csv
ssc-calc run gs.means --example --docx report.docx   # the report as a Word document too
ssc-calc eval pnt 2.0 10 1.5 1                  # distribution functions
```

Inputs are `id=value` pairs using the parameter ids listed by `show`. Use
`--json` for the full result, `--docx FILE` to save the report as a Word
document as well, and `--threads N` to limit the cores used.
Ctrl-C cancels a running calculation.

### Language models (MCP)

`ssc-mcp` serves the calculator to language-model clients (Claude, ChatGPT,
Codex, coding agents) through the Model Context Protocol: three read-only
tools to find a method, see its inputs, and calculate, with the engine doing
the arithmetic. Install the extra and add it to a client:

```bash
pip install ".[mcp]"                        # from a clone: the engine and the MCP SDK
claude mcp add sample-size -- ssc-mcp       # Claude Code; other clients start the same command
ssc-mcp --transport http --port 8000        # or host it: Streamable HTTP at /mcp
```

[docs/mcp.md](docs/mcp.md) covers the clients, hosting (a Docker image), and
listing it in the Claude and ChatGPT directories and the MCP Registry.

### Python

```python
import ssc

res = ssc.run("means.two.t", "n", {"power": [0.8, 0.9], "mu1": 1, "mu2": 0, "sigma": 1})
for row in res["rows"]:
    print(row["n1"], row["n2"], round(row["power"], 4))
# 17 17 0.807
# 23 23 0.9125

ssc.catalog()                 # categories and procedures
ssc.search("kruskall walis")  # ranked matches: {"corrected": "kruskal wallis", "hits": [...]}
ssc.schema("gs.means")        # parameters of one procedure
ssc.evaluate("qt", 0.975, 10, 1)
```

`ssc.run` releases the GIL while the engine works, so calculations can run in
a background thread. Pass an `ssc.Token()` as `token=` to cancel them or read
their progress.

## How it is built

```
core/                     C++17 engine (standard library only)
  include/ssc/ssc.h         C interface: JSON request in, JSON result out
  src/stats/                distributions: normal, t, χ², F, beta, gamma, binomial, Poisson,
                            noncentral t/χ²/F/beta, bivariate normal, sample correlation
  src/engine/               procedure registry, input parsing, scenario expansion,
                            thread pool, power curves, procedure search, JSON
  src/procedures/           the statistical procedures
  tests/                    C++ tests and reference values
python/ssc/               Python package: ctypes bindings, ssc-calc, and the MCP server
                          (mcp_server.py)
tests/                    Python tests (bindings, command line, MCP server, properties)
web/                      the web page, on the engine compiled to WebAssembly
.github/workflows/        CI, the wheels, and the web page's publishing (pages.yml)
scripts/                  development tools: a virtual environment, stress tests, the
                          Temme coefficients
packaging/mcp/            the MCP server's Docker image and registry entry
docs/api.md               the C interface and the JSON request/result format
```

- **Layers.** In Python, the engine is reached through one set of bindings
  (`ssc.core`), which the command line and the MCP server both call directly.
  The MCP server is an optional outer layer for language-model clients:
  nothing else goes through it, and the package runs without the MCP SDK (a
  test checks both). The web page calls the same C functions in the engine
  compiled to WebAssembly, from a Web Worker.
- **Parallelism.** Scenarios, power-curve points and simulated studies are
  spread over a pool of worker threads, started once and kept. Work nested in
  a scenario (its simulation, a numerical integral) goes to the workers that
  are free, so two or three scenarios still use every core, and calculations
  running at the same time share the workers instead of competing for the
  cores. The pool uses every core by default (`threads=` or `--threads`
  change this). Results are identical for any number of threads.
- **Numerics.** Every distribution is implemented in the engine. Probabilities
  keep their relative accuracy in the tails, and the code covers extreme
  parameters: Temme's expansion for the incomplete gamma function, and
  Poisson-mixture integrals for noncentrality parameters up to 10³⁰. Exact
  power calculations enumerate rejection regions; sample-size searches handle
  the saw-tooth power of discrete tests.
- **Interface.** The engine describes every procedure: parameters, choices,
  dependencies between inputs, solve-for options and report columns. The web
  page's forms, the command line and the MCP server's tools are built from
  these descriptions, so a new procedure needs no user-interface code.
- **Search.** The engine indexes every procedure's name, keywords, parameters,
  summary and references. Matching is inexact: misspellings are found
  through a trigram index and a bounded edit distance, and synonyms and
  abbreviations map to shared terms. Results are ranked with BM25, at a few
  hundredths of a millisecond per query ([details](docs/api.md#search)).

```bash
.venv/bin/pytest                                           # Python tests
```

The web page's engine is built with the Emscripten SDK (`web/build.sh`), and
the engine's C++ tests also run under Node as WebAssembly; see
[`web/README.md`](web/README.md). The *Pages* workflow builds the page and
its engines and publishes them to GitHub Pages whenever a push to `main`
changes the engine or the page. Only the page is published, not the rest of
the repository.

The source tree finds the engine in `build*/` automatically. Set `SSC_CORE_LIB`
to use a library in another location.

## Validation

- **Distributions.** 5,695 reference values from R and 222 high-precision values
  from `mpmath` cover every function, including far tails and extreme
  parameters. Typical relative errors are 10⁻¹⁴ to 10⁻¹⁵.
- **Procedures.** 174 calculations, covering all 61 analytic procedures, are compared
  with independent computations in R:
  - `power.t.test`, `power.anova.test`, `power.prop.test` and the `pwr` package;
  - `rpact` for the survival and group-sequential designs;
  - `mvtnorm` for co-primary endpoints;
  - enumeration of exact tests with `binom.test`, `fisher.test`, `prop.test`,
    Poisson tail probabilities and Farrington–Manning and Miettinen–Nurminen
    score tests;
  - brute-force searches for Simon's two-stage designs and for saw-tooth
    sample sizes;
  - generalized least squares on the full design for the stepped-wedge and
    longitudinal-slope designs, and the full correlation matrix for repeated
    measures;
  - the published variance formulas of Zhu & Lakkis (negative binomial rates)
    and Donner & Klar (cluster trials), and the formulas of Schlesselman and
    Dupont (case-control studies) and Connor (two diagnostic tests);
  - numerical integration for TOST and the correlation coefficient;
  - published results: PowerTOST (bioequivalence), Simon (1989),
    Newcombe (1998), and pmsampsize with the worked examples of Riley et al.
    (2020) for prediction models.
- **Group-sequential designs.** These agree with `rpact` to about 10⁻⁸ in power
  and expected sample size. That includes β-spending futility boundaries
  (binding and non-binding) and fixed futility boundaries.
- **Simulation.** The random streams and variates are checked against their
  moments, and binomial variates against the exact probabilities; the
  mixed-model fits reproduce the ANOVA estimates of a balanced
  random-intercept design, the two-stage analysis of complete random-slope
  data and a dense REML likelihood with dropout; Satterthwaite's degrees of
  freedom are exact where theory says so. The logistic mixed model's
  quadrature matches a brute-force integral; its fit is a stationary point of
  the likelihood, also with clusters of a million subjects, single-subject
  clusters and very large ICCs, recovers a large between-cluster SD without
  bias and reduces to logistic regression without overdispersion; and its
  scale conversions (population-averaged and typical-cluster proportions,
  latent and proportion-scale ICC) are exact. The survival simulation's
  statistics match the published logrank test of the 6-MP leukemia data, its
  multivariate normal probabilities match known orthant values, and under
  proportional hazards its quick approximation equals the logrank formula and
  its simulated power and events agree with it. For balanced designs the simulated
  power agrees with the exact power within its Monte Carlo error, the type I
  error is close to α, results depend only on the seed (not on the thread
  count), and a solved sample size is the smallest whose simulated power
  reaches the target.
- **More simulation designs, against R.** The proportional odds fit equals
  `ordinal::clm` to 10 digits and the MMRM fit equals `nlme::gls` (ML and
  REML); Dunnett's critical values give a familywise error of exactly α by
  `mvtnorm::pmvt`, and the exact single-step powers agree with it to 5
  decimals; the win ratio's counts by sorting equal the counts over every pair,
  ties included. Simulated powers agree within Monte Carlo error with R doing
  the same simulations with its own tools: `t.test` and `wilcox.test` for
  skewed and heavy-tailed data, `p.adjust` and `multcomp` for Holm, Hochberg
  and Dunnett, `MASS::polr` for ordinal outcomes, `lmerTest` for stepped-wedge
  trials, and an independent implementation of the pairwise comparisons for
  the win ratio.
- **Stress tests.** Every simulation procedure is fuzzed with random and
  extreme inputs (huge samples, near-degenerate correlations, almost all
  patients lost), run with 1 to 16 threads (results must be identical),
  run concurrently from many threads, cancelled at random moments, run with a
  million simulated studies, and checked for its type I error at several null
  designs (`tests/test_stress.py`; `scripts/stress_simulations.py` runs the
  long version). A long simulation holds one block of 16,384 simulated
  studies at a time and gives freed memory back to the system when it ends.
  The engine and its tests also
  run under AddressSanitizer, UndefinedBehaviorSanitizer and
  ThreadSanitizer.
- **Whatever is typed.** Every input of every method, in every solve mode,
  gets a battery of 65 typed texts (25 for a list) (blank, letters, decimal commas, 1e-300
  and 1e300, inf and nan, bad ranges, a list of 3,000 values ...): each run
  must end promptly, with an answer or a clear message, and Stop must end it
  (`scripts/stress_inputs.py`; `core/tests/test_extremes.cpp` keeps the cases
  that once ran forever). Counts are limited to a billion, and one simulated
  study to a million subjects, measurements or clusters (200,000 patients for
  the win ratio), so that Stop, which acts between studies, is prompt.
- **Properties.** Tests generated from each procedure's schema check every
  solve mode: a solved sample size or effect gives back the target power,
  sample sizes are the smallest that reach it, power never falls as α grows,
  and results don't depend on the thread count. Seeded random inputs (40 per
  procedure in the test suite, 300 per procedure in a longer sweep) must give
  a finite result or a clear message, within a time budget.
- **Search.** A benchmark of 179 queries a user might type (names,
  abbreviations, synonyms, typos, Greek letters, partly typed words) checks
  that the expected procedure comes first or among the first few, and that
  every procedure is found first by its own name and id.
- **Engine behavior.** The tests also check that cancellation works and that
  inputs are validated.
- **The web page.** The C++ tests pass under WebAssembly, and every method
  and solve-for choice gives the native answer to within 4 parts in 10¹². The
  page was tested in a browser across all methods, choices and thousands of
  random combinations of options ([`web/README.md`](web/README.md)).

The reference values are stored with the tests in `core/tests/fixtures/`.
They were computed once, independently of the engine, with R 4.3.3 (`pwr`
1.3.0, `rpact` 3.4.0, `mvtnorm` 1.2.4) and `mpmath` 1.4.1; running the tests
needs none of these.

The longer random sweep runs from the test suite:
`SSC_FUZZ_CASES=300 python -m pytest tests/test_properties.py -k fuzzed`.
